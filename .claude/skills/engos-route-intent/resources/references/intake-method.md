# Distinguishing the result needed next

Load this reference when an ambiguous outcome or depth needs more reasoning than
the skill entry provides. It contains examples, not an intake form or a closed
routing list. The entry owns question-interface, authority and acceptance rules;
use `question-tools.md` only when the actual host interface needs checking.

## Use the task's relevant facts

The next decision may depend on the desired artifact, audience, accepted revision,
missing evidence or allowed effort. Use only relevant dimensions: audience can
change a presentation, but not necessarily a demonstrated boundary fix; code layout
can matter for implementation, but not for an inbox attention queue. A supplied
specification may settle an audit's purpose without another question.

| Result still missing | Distinction to make |
| --- | --- |
| Understand a problem before selecting a solution | A solution-free frame identifies people, outcome, actual appetite and uncertainties. |
| Define an identifiable change's behavior and acceptance | A specification preserves existing decisions and unchanged behavior. |
| Choose among competing material | Compare actual sources and criteria; do not fabricate an absent alternative. |
| Work through research and shaping to a reviewed team-decision proposal | The shaping conductor owns that workflow, including G0–G4 and real engineering/team/betting decisions. A plain-language request can establish this depth. |
| Perform an established job | Plan accepted scope, implement a bounded slice, review an actual artifact, produce a report/presentation or use another current owner directly. |

“Smallest useful” means sufficient for the requested result, not always the
shortest artifact. Conversely, an unclear word or absent document does not justify
adding the entire workshop. Optional helpers remain separately wanted outcomes.

## Worked ambiguity

After reading onboarding notes that describe complaints but no desired decision:

> Your notes do not yet state the outcome to improve, so I recommend clarifying
> the problem first. What result would help next?
> A. A clear problem and desired outcome.
> B. Defined feature behavior and acceptance checks.
> C. Researched options and a reviewed proposal for a team decision.
> Other — describe the result you need, correct my premise, or say you are unsure.

If the user already requested C, skip this question and select the shaping owner.
If the answer is uncertain, explain what the recommended artifact would establish
and what later evidence would justify more depth; it does not authorize C.

## Different jobs need different questions

- **Missing comparison input:** “I have proposal A but not B. Supply B if you want
  that comparison, or Other — describe the intended task or another answer.” An
  invented opponent is not a useful shortcut.
- **Ambiguous audit:** “Your notes emphasize maintainability, so I recommend a
  code-health audit. Do you need A) structural risks, B) completeness against the
  supplied feature scope, C) project activity over a period, or Other — describe
  the decision or correct my reading?” Do not ask if the supplied purpose settles it.
- **Incident material:** distinguish active coordination, retrospective operational
  review and diagnosis of one failure using the user's desired result. Ask only
  if the distinction remains material, with the same Other/free-text path.
- **Presentation/report:** a clear request for slides or a weekly brief already
  identifies an artifact. An audience question is useful only if it changes the
  output; a general product interview is not.

After an answer, update only affected facts and ask the next still-material
question. Stop intake when the next authorized job is clear enough. Preserve the
receiving owner's actual questions, decision gates and requested stopping scope;
the examples do not replace its contract.
