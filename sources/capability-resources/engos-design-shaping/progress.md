# Explain progress without inventing completion

Use this route on "where are we", "what is blocked", "show progress", after a
material handoff, and on resume. Resolve the existing run and load the gate
capability's progress/runtime instructions and actual helper help before invocation.
Use its versioned projection for all views; do not derive a competing state from
chat, filenames, an author's status label or `status: consistent` alone.

Lead with the requested outcome and current action, then show Intake, Framed,
Research, Shaped and Bet-ready only as applicable to the requested stopping point.
Framing-only completion leaves later stages outside scope, not failed. Keep latest
accepted revision distinct from a newer draft needing review or repair. A document
written, a gate verified, a target saved, and a human bet are separate events.

Show the actual assigned role/actor or unassigned; the precise blocker and needed
resource/decision; next permitted action; current draft/accepted artifact links;
content/visual/per-target delivery status; and snapshot/last-observation times.
Separate implementation appetite from interview effort. Counts of verified gates
describe gate coverage, never percentage of effort, savings or predicted finish.

Explain missing evidence in ordinary language, with a concrete example of the
smallest useful input. Retain the original technical term when needed, but define
it from inspected context rather than expecting a novice to design the investigation.
Distinguish an assigned worker from an unassigned human respondent. Do not invent
a person, reinterpret the user's requirement or paraphrase away uncertainty.

Only the controller records attributable host observations, bound to current
run/version/generation/attempt. Observations describe activity, not acceptance.
Dispatch is queued, not proof of execution; an old started event is only last
observed activity. Silence is not consent or proof of a hung worker. Missing or
corrupt state is unverifiable. Reopen/drift follows the gate runtime, not a UI rule.

Simulation must remain prominent in every projection. Do not assign a real owner,
confirm investment or claim live operations from model role-play. Explain exactly
which human/evidence checks remain unobserved without repeatedly demanding humans
when the user requested a simulation exercise.

Refresh on recorded events or explicit status/resume, not an invented background
monitor. Generated Markdown/HTML/JSON are as-of views from the same record. External
status publication/updates require actual target authority and preserve edits;
local receipt integrity does not prove a remote target stayed unchanged since its
last readback. A delivery-only failure preserves unchanged content approval.
