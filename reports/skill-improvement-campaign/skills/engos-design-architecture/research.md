## Current authoritative practice and useful resources

The pages below were actually opened. “Supports” records the source claim; “implication” is our proposed use. None is a model efficacy claim. The capability should use existing project formats/tools, not install every listed option.

| S1 | [RFC 9110, §9.2.2 and conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html) | Idempotent methods concern repeated intended effects; retries and preconditions have defined HTTP semantics | Distinguish method semantics from domain operation deduplication. Source does not prescribe our job-key storage design |
| S2 | [RFC 9457, Problem Details and §5](https://www.rfc-editor.org/rfc/rfc9457.html) | Structured error details need scrutiny for privacy/security disclosure | Give useful errors and validation examples while restricting internal details. Existing domain error formats can remain appropriate |
| S3 | [OpenAPI 3.2.0, Security Requirement Object](https://spec.openapis.org/oas/v3.2.0.html) | Combined schemes and alternative requirement entries differ; an empty object permits anonymous access | A machine-readable contract can make subtle auth shape reviewable. | S5 | [PostgreSQL 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html) | Read Committed and Repeatable Read have different anomaly behavior; serialization failures can require whole-transaction retry | Specify concurrent schedules and failure handling rather than “use a transaction” |

| S7 | [AWS transactional outbox, intent/issues/implementation](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) | DB/event dual writes can diverge; a same-transaction outbox and idempotent consumer address relevant seams | Consider outbox/CDC only for matching boundaries; do not infer atomic object/index effects or end-to-end exactly-once behavior |
| S8 | [Google SRE, Handling Overload](https://sre.google/sre-book/handling-overload/) | Overload needs degradation/errors and resource-aware capacity; QPS can be a poor resource proxy | Add finite backlog/admission/fairness and downstream resource analysis. | S9 | [Google SRE Workbook, Implementing SLOs](https://sre.google/workbook/implementing-slos/) | User-oriented SLIs need a measurement implementation; different observation points miss different failures | Tie reliability claims to measurable journeys and ownership, not just uptime adjectives |

| S11 | [Michael Nygard, Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | Context, decision, status and consequences preserve rationale; superseded decisions remain useful | Explicit proposed/accepted state, consequences and revisit criteria in the decision log |

## Alternatives and recommendation

**Retain the incumbent.** It has substantial useful coverage and no valid comparison establishes a loss. Retention remains the actual state until a candidate wins. This is also the correct result on ties or invalid measurements.

**Focused monolithic reinforcement.** Add concurrency/recovery and quantitative checks within the current body, preserve its output layout. Lower packaging and delivery risk; useful if current models already ignore irrelevant sections or if selective loading creates omissions. It does not directly address competing format demands or repeated output overhead. Keep as a defensible subsequent hypothesis if resource delivery adds burden or loses coverage.

**Recommended experimental direction: shared decision workflow plus complete mode resources.** One response contract preserves all substantive output meanings and the current scorecard criteria/thresholds, clarifies applicability and hard vetoes, and selects full playbooks only for the needed modes. Add mechanism-level contract checks and concrete adverse examples where textual coverage was thin. All content remains under the existing slug and advisory boundary. Use the existing `CapabilityResourceMap.v1` loader/build machinery, not a new execution framework. The candidate is complete under [candidate/](candidate/), with no canonical edit.

Measured package sizing: the candidate entry is 14,904 UTF-8 bytes; entry plus all five guide files is 40,372 bytes, versus incumbent SSOT 27,572 bytes. Individual mode inputs, including their public task, are about 23.9–26.3 KB before host overhead; the three-mode service-split input is about 37.1 KB. Thus the redesign adds substantial total guidance and does **not** establish a general context reduction. The primary hypothesis is better decisions; selective loading may save some single-mode input but may cost more for mixed work. See `sizing.json` for exact per-case values.

This is a **joint hypothesis**: organization, mode-specific reasoning aids, applicability and score anchors change together. A win would be a package effect, not proof that compression alone works. If attribution matters after a valid package signal, preregister monolithic-reinforcement versus selected-resource ablation as a later round. Do not silently derive causality from bytes saved.

**Split/addition considered but not selected.** Dedicated migration-design or API-design capabilities could improve discovery, but all currently identified jobs fit existing Architecture modes. A recurring independently requested execution/verification job would instead overlap Testing, Code Review or GitOps and need a different authority contract. No distinct unmet job has enough local evidence to justify another capability now. Coordinator owns any future intake and routing boundary decision.

Flip conditions: retain current/focused form if selected resources are missed, preparation/reading cost exceeds useful gain, short output omits required reasoning, mixed-mode coherence regresses, or the trial fails hard controls. Consider a new capability only when distinct users/jobs and output/authority boundaries survive overlap review. A faster/cheaper model can change the deployment recommendation only after equivalent task outcomes and measured burden on the same skill.


## Revision following fresh independent challenge

The preservation map now explicitly identifies the relaxation of universal interface-only replacement, universal dependency wrapping and explicit-constraint-only vendor selection. These are intentional applicability changes, not proven equivalent wording. Replacement and isolation costs must follow actual boundaries/change pressure, and explicit caller vendor/framework/portability constraints remain binding. This avoids mechanical wrappers while preserving constraint fidelity.

The first workload/PAT/DB controls closely match instructional examples; their role is teaching/control fidelity, not transfer. Five added cases change workload or domain constraints, include a feasible simple capacity design, and require an ordinary catalog design from actual schema/API files. Numeric controls read structured fixture data; semantic prompt/expectation alignment still needs review. Seventeen public cases remain authored examples. RPC, webhook and event-contract breadth is explicitly unmeasured.

The recommended next experiment is a small fixed-model discriminating comparison after an admitted preflight. The prior broad count/model-screen sequence is historical, not required. Detailed runtime diagnostics are not part of this public revision; aggregate status is runtime not admitted. Raw-source design acceptance remains separate from later UAC/generated-treatment integration.
