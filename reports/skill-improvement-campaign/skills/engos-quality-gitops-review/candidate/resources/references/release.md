# Package, tag and release evidence

Start from the project's real packaging/release script and contract. Some flows build from a tag, others prepare artifacts before tagging. Separate prerequisites from actions and derive their dependency order; do not assume every project needs a new signing system, container image, package registry or second provider.

## Package readiness
Identify source commit/tree, any included working-tree changes, version/changelog, generator state, build entrypoint, relevant toolchain and dependency inputs, expected artifact names/content and required validation. Inspect existing artifacts without executing their code. A success exit or familiar extension does not prove correct contents. Compare manifests, included/excluded paths, metadata and digests against the intended deliverable; distinguish generated source archives from built/installable packages. For Python, for example, source distributions and wheels serve different purposes and may carry different files.

When a reproducibility claim matters, require the declared source, environment and build instructions plus independent rebuild comparison under that definition. A digest match between two downloads only proves equal downloaded bytes. It does not demonstrate independent reproducibility or product behavior. If a build is explicitly authorized, preserve original evidence and record resulting inputs, artifacts and validation. No silent package build in advisory mode.

## Tag and publication readiness
Resolve tag object and peeled commit target, intended source, signatures if required, and tag state on every required remote. A version name is not immutable identity. Existing conflicting tags are a blocker requiring a separately reviewed recovery decision; do not force-replace them. Check the actual release object, draft/prerelease state, expected assets and destinations, applicable hosted runs, changelog and release-facing docs.

For publication verification, obtain the expected asset from each required provider and compare its digest/content to the reviewed package. Inspect download failure, redirect and unexpected content; a release link can point elsewhere, and a source archive is not the packaged output. An HTTP success does not prove a package was received. Do not send credentials to an unrelated redirect host or broaden access to complete a check.

If provenance/attestation policy applies, verify the artifact digest against the attestation subject and all fields constrained by the project's trust policy. Check signer/builder/source, the build type and external parameters where applicable, including policy handling of unrecognized parameters and explicitly permitted exceptions. Matching digest, builder and source cannot compensate for a disallowed build parameter. If a constrained field is absent or cannot be checked, report that evidence gap rather than inventing compliance. Presence of an attestation, a successful signature check alone or an SBOM does not prove that the artifact is safe or built from the intended source. Missing optional attestation is an improvement opportunity, not an invented release blocker. `gh release verify` and `gh release verify-asset` can verify supported immutable-release attestations when installed CLI and release support are present; the latter does not verify generated source zip/tar archives. Check current help first.

## Completion and recovery
Report source reviewed, package built/validated, tag verified, publication/download verified, installed parity and live acceptance as distinct facts. Installation needs its own requested target, exact write set, comparison with existing customization and readback. Release verification alone does not authorize installation or prove runtime acceptance.

After a partially completed authorized publication, record which provider/assets/tags exist and their digests. Inspect before any retry; do not duplicate releases, replace bytes or move tags to disguise divergence. Give the next recovery action and remaining authority explicitly. Rollback may require a new version or forward repair under project policy; deleting history is not a default recovery procedure.
