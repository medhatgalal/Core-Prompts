# Unified chat scenario

Constructed teaching fixture inspired by contrasting framed/shaped documents.
It intentionally lacks critical feasibility evidence; a correct stop is useful.

Raw input: "Make development chat-first. One place to plan, build and see results."

Scenario decision U1: one month, two engineers. Desired outcome: one persistent
development conversation survives reload and connects planning with building.
Walk away or reshape if the usable core cannot fit the month. Exclude cross-app
work, an application-level planning product and broad performance hardening.

Fixture facts:
- The product currently has separate plan and build conversations and loses
  navigation context on reload. A reusable React chat component exists.
- ProductOwner selects the user outcome; Engineering owns feasibility research.
  An existing HostHarness coordinates work, while PreviewAPI supplies renderable
  design-object content. The hypothetical caller already uses session authentication.
- A conversation persistence API exists, but the fixture contains no proof of
  its compatibility with reload/navigation or the combined harness session model.
- Inline object preview across all supported authentication modes is desired.
  There are no API specifications or executed prototype results supplied for that seam.
- A document titled "Shaped" asserts "ready" and "prototype confirmed" but
  attaches no code citations, run records or results. Treat that label as a claim.
- A pre-existing sub-agent feature is in development. No completion evidence is
  supplied. Streaming versus completion-only results is not yet a scoped decision.

No permission to invent internals, APIs or prototype results. Research must name
which missing evidence blocks the bet and a bounded spike with an owner role,
success/failure criteria and impact. Stop before Shaped if it remains unresolved.
