# Skill Job Map

This is a plain-English routing map, not behavioral proof and not a merger plan. The canonical behavior remains in `ssot/`.

Portfolio actions mean:

- `keep`: the boundary is already focused.
- `keep_and_clarify_boundary`: preserve the skill and sharpen how it differs from neighbors.
- `keep_but_review_scope`: preserve it, then test whether its Swiss-army or advisory scope is too broad.
- `experimental_keep_pending_evidence`: keep the experiment separate until routing and preservation evidence exists.
- `keep_and_improve_process`: preserve the capability and improve its evidence or workflow controls.
- `draft_new_skill_pending_review`: UAC created a safe placeholder; a human must review its job and neighbors.

No skill is marked for merger or deletion because current evidence does not justify either action.

## Routing Questions

- `address-code-review`: Are we finding problems, or applying already-selected review feedback?
- `analyze-context`: Does the investigation need resumable reasoning state rather than a one-time report?
- `architecture`: Is the deliverable a technical design, or merely a recommendation among existing options?
- `auto-research`: Do we need evidence of better behavior, or only a stronger draft?
- `code-review`: Are we reviewing code for defects, applying feedback, or checking release mechanics?
- `codebase-health-audit`: Is the question about code structure, product completeness, or delivery activity?
- `converge`: Are there multiple competing inputs that must become one decision?
- `demo-recorder`: Is the browser flow meant to prove behavior or communicate it as a demo?
- `docs-review-expert`: Is the problem document-system health or sentence-level instruction editing?
- `dynamic-html-presentations`: Is the main artifact a deck, a live product demo, or a written report?
- `eng-report`: Is the question about engineering activity, product completeness, or code health?
- `feature-status`: Are we asking whether the product feature is complete, how the repo is structured, or what activity occurred?
- `gitops-review`: Is the blocker in code correctness or in the path from repo state to release?
- `ic-assistant`: Is there an active incident with a commander and a required process?
- `instruction-editor`: Is the goal clearer language, a stronger artifact, or proof that behavior improved?
- `mentor`: Does the user need coaching and sequencing, a technical design, or a final choice among options?
- `pitch`: Is this a future investment pitch, a current feature status check, or a general decision synthesis?
- `pulse`: Is this personal communications triage, incident process, or a periodic intelligence report?
- `resolve-conflict`: Is there an actual merge conflict to resolve, or merely disagreement among proposals?
- `supercharge`: Does the user want the artifact strengthened, or evidence that one strengthened variant performs best?
- `testing`: Is the main task to test behavior, review code, or prove release readiness?
- `threader`: Are we exporting the conversation, or maintaining an ongoing evidence investigation?
- `uac-import`: Are we importing a capability, editing instructions, or proving behavior?
- `weekly-intel`: Is the report multi-source and executive, repo-activity focused, or about one feature's completeness?
- `batman`: Does this request directly require Batman — Evidence-Gated Delivery Controller?
